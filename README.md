# 🔐 Warpvault

> **Zero-knowledge secret sharing for people who don't want their production credentials floating around in Slack.**

Paste a password, an API key, a `.env` file or a private key. Your browser (or terminal) encrypts it with **AES-256-GCM** before anything touches the network, and you get a link. The decryption key lives only in the link's `#fragment`, which browsers never send to a server, so **the server stores ciphertext it can't read**. By default the secret destroys itself the first time it's opened.

Part of the Warp family: [Warpstash](https://github.com/BioHazard786/warpstash) (temporary file hosting), [WarpDrop](https://github.com/BioHazard786/warpdrop) (device-to-device transfer) and Warpvault (secrets).

👉 **Live:** [vault.warplabs.info](https://vault.warplabs.info)

---

## 🎯 Why You'll Love It

- 💥 **Burn After Reading**: the default. Opening a secret atomically deletes it from disk and database.
- 🔑 **True Zero-Knowledge**: AES-256-GCM, so tampering is detected too. Encryption runs in your browser (Web Crypto) or the Go CLI. [The format is specified](protocol/PROTOCOL.md) and both implementations are tested against shared vectors generated by a third implementation.
- 🔒 **Optional Passphrase**: the link carries a random key and the passphrase is mixed in (PBKDF2, 600k rounds), so a leaked link alone can't open it, and the passphrase alone can't be brute-forced.
- 🤖 **Preview-Bot Proof**: Slack, Discord and iMessage love to open links. Opening a secret is a `POST`, and the page asks you to press *Reveal*, so crawlers never burn it. The creator's delete link also asks before it deletes.
- 🛟 **Typo-Proof**: a wrong passphrase doesn't cost you the secret. The ciphertext is kept in the tab, so you can retry without asking the server again.
- 💻 **Terminal Native**: a standalone CLI that sends from stdin, files or arguments and decrypts on the way back.
- 📱 **QR Handoff**: show a link as a QR code to move a secret to your phone.
- 🪶 **Stupidly Lightweight**: one small static binary with SQLite built in.

## 🚀 CLI in 5 Seconds

```bash
# Install (Linux, macOS, Windows via Git Bash)
curl -fsSL https://vault.warplabs.info/install.sh | bash
# or: go install github.com/BioHazard786/warpvault/cli@latest

# Send piped text (burns after one read)
echo "sk_live_999888777" | warpvault

# Send a file and keep it for 12 hours
warpvault send -f ~/.ssh/id_ed25519 --expiry 12h

# Require a passphrase too (prompted without echo; or set WARPVAULT_PASSPHRASE)
warpvault send -p "the staging database password"

# Read it: text goes to stdout, files are saved under their original name
warpvault get "https://vault.warplabs.info/v/a8X2mP9z#KEY"
warpvault get "https://vault.warplabs.info/v/a8X2mP9z#KEY" -o ./id_ed25519
```

### Self-hosted server

Install from your own server and the CLI already points at it, nothing to configure:

```bash
curl -fsSL https://vault.example.com/install.sh | bash
```

(Your server writes its `WARPVAULT_BASE_URL` into the script it serves. Set `WARPVAULT_NO_CONFIG=1` to skip that.) Installed some other way (`go install`, Homebrew)? Save the server once:

```bash
warpvault config set server https://vault.example.com
warpvault config set auth-token        # only if the server needs one; asked without echo
warpvault config get                   # what is in effect, and where it comes from
```

Precedence, highest first: `-s` flag, `WARPVAULT_SERVER`, the saved config, the built-in default. The config file is `~/.config/warpvault/config.json` (`warpvault config path` prints it, `WARPVAULT_CONFIG` overrides it) and is readable only by you. A saved token is only ever sent to the server it was saved for, and `get` never sends one: opening a secret needs no token, and a link can't make the CLI hand a token to its server.

## 🐳 Self-Hosting

### Docker Compose (prebuilt image)

```bash
curl -O https://raw.githubusercontent.com/BioHazard786/warpvault/main/docker-compose.yml
cp .env.example .env   # set WARPVAULT_BASE_URL at least
docker compose up -d
```

The compose file publishes on `127.0.0.1:8080` only (put Caddy or Nginx in front), runs read-only with all capabilities dropped, and has a healthcheck. `docker compose up -d --build` builds from source instead.

### Production with Caddy

```bash
cp deploy/production.env.example .env        # set WARPVAULT_BASE_URL (and optionally an auth token)
docker compose up -d                          # listens on 127.0.0.1:8080 only
sudo cp deploy/Caddyfile.sample /etc/caddy/Caddyfile   # set your domain, then: sudo systemctl reload caddy
```

[`deploy/Caddyfile.sample`](deploy/Caddyfile.sample) handles TLS, compression and HSTS, and overwrites `X-Real-IP` so clients can't spoof their address to the rate limiter. Leave access logging off: delete links are credentials.

### Bare metal

```bash
make build            # SPA -> backend/web/dist, then the server and CLI binaries
./warpvault-server --port 8080 --base-url https://vault.example.com
```

### Reverse proxy

Set `WARPVAULT_TRUST_PROXY=true` and `WARPVAULT_BASE_URL=https://vault.example.com` behind a proxy so rate limiting sees real client IPs and links are HTTPS.

```caddy
vault.example.com {
    reverse_proxy localhost:8080
}
```

## ⚙️ Configuration

| Setting | Default | What it does |
| :--- | :--- | :--- |
| `WARPVAULT_BASE_URL` | `http://localhost:8080` | Public URL used in share and delete links |
| `WARPVAULT_PORT` | `8080` | Port the server listens on |
| `WARPVAULT_MAX_SECRET_SIZE_MB` | `25` | Largest secret, in MB (includes ~50 bytes of encryption overhead) |
| `WARPVAULT_DEFAULT_EXPIRY` | `burn` | Used when a client doesn't say (`burn`, `1h`, `12h`, `24h`, `72h`) |
| `WARPVAULT_ALLOWED_EXPIRIES` | `burn,1h,12h,24h,72h` | Lifetimes the UI offers and the API accepts |
| `WARPVAULT_AUTH_TOKEN` | *(none)* | If set, creating secrets needs this token. Reading needs none |
| `WARPVAULT_TRUST_PROXY` | `false` | Trust `X-Forwarded-For` / `X-Real-IP` (only behind a proxy you control) |

More in [.env.example](.env.example).

## 🧱 Layout & Development

```
backend/    Go server (chi, SQLite). Embeds the SPA from backend/web/dist
cli/        the `warpvault` CLI, its own Go module
web/        Vite + React + TanStack Router + shadcn/ui
protocol/   the wire format spec + shared test vectors
```

```bash
make dev-web   # Vite on :5173, proxying /api to a server on :8080
make run       # build the SPA and run the server
make test      # backend + cli + web tests
make fixtures  # regenerate protocol/fixtures/vectors.json
```

**Where is my data?** The server stores everything under `./data` relative to the directory you start it from (the startup log prints the absolute paths): `data/warpvault.db` (SQLite) and `data/storage/<aa>/<bb>/<id>.enc` (one encrypted blob per secret; unreadable without the link's key, by design). In Docker it's the `warpvault_data` volume mounted at `/data`. `make clean` removes build output only; `make clean-data` deletes `./data`.

The server can only store and delete: it never holds a key, so a full database leak yields no plaintext. What it can see is metadata: sizes, timing, and uploader IPs (kept for abuse handling). See [PROTOCOL.md](protocol/PROTOCOL.md) for the exact format and threat model.
